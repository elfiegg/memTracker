# Kimi-K3, 256 GPUs: fit remains unproven

The requested configuration has **no verified full-training fit result yet**.
A source-derived state lower bound is below GB200 capacity. A real GPU probe
verified lazy pipeline receive allocation, but did not execute K3 training.

## Recipe and assumptions

Full 93-layer Kimi-K3; 896 routed experts, top-k 16, forced round-robin; 256 GB200s;
PP8/FSDP32/EP32/TP1/CP1, DP replication 1; native 1F1B; sequence **4068**;
microbatch **2 × 64**; BF16 primary parameters and compute; FP32 reduction;
DistMuon + AdamW, learning rate 8e-4, weight decay zero; FullAC; HybridEP;
CUDA graphs off; no QAT. Global batch is 4096 sequences.

The source recipe explicitly uses `fsdp_reshard_after_forward="always"`.
BF16 primary storage, the full Kimi-K3 model identity, GB200 hardware, and
synthetic text-only input are assumptions inherited from the surrounding
experiment. Vision parameters are present in the full run; vision execution is
not exercised by text-only input.

The training source is `b4d5b404bd30dec67f86873203fbd4ba5f457531`.
The native partition is **11/12/12/12/12/12/12/10 layers**, with embedding/output
weights influencing the split. Executed source partition/layout functions and
checksums are recorded in [source verification](../experiments/k3_fit_source_verification.json).
The existing shape inventory supplies the parameter arithmetic; this experiment
does not pretend that arithmetic is a complete FakeTensor model execution.

## What is counted

For a stage with 12 MoE layers, EP32 leaves 28 experts per GPU per layer.
EP overlays FSDP here: EDP=1. Applying a second EP divisor would undercount state.

| Source-derived quantity | GiB per GPU |
|---|---:|
| BF16 local expert parameters | 20.672 |
| FP32 local expert accumulated gradients | 41.344 |
| Minimum BF16 expert Muon momentum | 20.672 |
| Expert-only steady-state lower bound | **82.688** |
| Sharded BF16 dense decoder parameters | 0.406 |
| Unreduced FP32 dense decoder gradients | 25.965 |
| Combined decoder steady-state lower bound | **109.058** |
| Measured GB200 capacity | **184.346** |

The combined bound assumes all counted decoder parameters participate in
backward. Pipeline FSDP disables gradient synchronization within the step;
FP32 gradient allocations persist after a no-sync backward. Expert momentum
persists after the first optimizer step. Sharded parameter storage is included;
additional gathered dense copies and dense optimizer state are omitted.

**109.058 GiB is a lower bound, not a peak prediction.** Missing terms include
checkpoint inputs/intermediates, KDA/MLA and MoE recompute workspaces, gathered
parameters, dense Muon/AdamW state, persistent Muon redistribution scratch,
NCCL and shared HybridEP backing, opaque dispatch handles, CUDA libraries, and
allocator slack. FullAC's recomputation policy must not be confused with the
SelectiveAC policy that explicitly saves communication outputs. HybridEP's
shared communication backing must not be multiplied by the number of layers.

## A runtime-dependent false OOM prediction

The local CPU helper runtime, PyTorch 2.14.1, eagerly allocates receive buffers
for all 64 microbatches. At stage 6, BF16 hidden states plus accumulated attention
residual stacks would occupy **104.282 GiB** in receive buffers alone. Adding
just expert state gives **186.970 GiB**, already over capacity.

However, the **recorded cluster runtime** `2.15.0.dev20260928+cu130` allocates
receive buffers lazily and transfers ownership into computation. Its setup
allocates **zero receive payload bytes**. Version strings alone are insufficient;
the probe records the installed methods' source hash and observed behavior.
The eager reference is a counterfactual, not an OOM result for this cluster.

Polyphe probe **463439** completed successfully on one GB200. It exercised the
installed receive allocation/ownership helpers for stage 6, retaining two
forward input payloads and one backward payload, then allocating synthetic
expert state:

| GPU probe checkpoint | Allocated GiB |
|---|---:|
| Receive setup | 0 |
| Two input payloads plus one backward payload | 2.390 |
| Above plus expert weights, momentum, FP32 gradients | **85.077** |

See [measured probe evidence](../experiments/k3_lazy_receive_gpu_probe.json).
These are allocation-only measurements. No communication or full-model compute
was executed, and synthetic co-residency does not establish actual training
lifetimes. The lower-bound screen uses **max(input floor, state floor)** for lazy
receives, rather than adding peaks whose simultaneous occurrence is unverified.

An initial probe, 463418, failed an assertion expecting eager allocation; it did
**not** OOM. The successful probe corrects that assumption.

## Reproduce the screen

```bash
PYTHONPATH=src python -m memtracker_nccl.k3_fit_experiment \
  --receive-policy lazy --output experiments/k3_256_pp8_dp32_ep32_s4068_fit.json

# Counterfactual for an implementation that eagerly retains all receive buffers.
PYTHONPATH=src python -m memtracker_nccl.k3_fit_experiment \
  --receive-policy eager --output experiments/k3_256_pp8_dp32_ep32_s4068_eager_reference.json

# On an allocated GPU with the target PyTorch runtime:
PYTHONPATH=src python scripts/probe_k3_pipeline_buffers.py \
  --scenario experiments/k3_256_pp8_dp32_ep32_s4068_fit.json \
  --stage 6 --output gpu-witness.json
```

The helper uses private PyTorch APIs and fails on unknown allocation behavior.
`helper_torch_version` identifies the runtime executing the metadata helpers;
`receive_policy` declares the target policy. The two are intentionally separate.

## Communication initialized eagerly: CPU-only comparison

Pipeline receive-buffer allocation and NCCL/HybridEP initialization are separate
settings. The new [communication budget experiment](../experiments/k3_eager_communication_budget.json)
keeps **all declared communication backing resident from the start through every
optimizer step**, independently of the receive policy. No discount is taken for
lazy communication initialization. This models lifetime, not an NCCL environment
variable that guarantees all real transport resources have been allocated.

For the target runtime's lazy pipeline receives:

```
remaining budget = 184.346 GiB capacity - 109.058 GiB state floor
                   - persistent communication backing
```

| Assumed total communication backing per GPU | Remaining for every omitted component |
|---|---:|
| 0 GiB (algebraic baseline only) | 75.288 GiB |
| 8 GiB | 67.288 GiB |
| 16 GiB | 59.288 GiB |
| 32 GiB | 43.288 GiB |
| 64 GiB | 11.288 GiB |
| 80 GiB | -4.712 GiB: exceeds capacity |

These inputs are **sensitivity assumptions, not measured NCCL/HybridEP sizes**.
Backing is counted once per GPU, not once per layer, microbatch, expert, or world
rank. Existing receive/payload tensor storage and imported peer mappings must not
be counted again. The remaining budget must cover activations, recompute and
optimizer scratch, additional gathers/dense optimizer state, CUDA/library memory,
communication temporaries, and allocator cached/pending/rounded backing.
A nonnegative budget means `not_ruled_out_by_partial_budget`, never proven fit.

With eager pipeline receives as well, the strongest stage bound is **213.340 GiB**
before any communication backing. This case **fails**, exceeding capacity by
28.994 GiB even at the zero-communication baseline. Expandable segments cannot
make this live-storage lower bound smaller; allocator overhead is omitted already.

```bash
PYTHONPATH=src python -m memtracker_nccl.k3_communication_budget \
  --communication-gib 0 8 16 32 64 80 \
  --output experiments/k3_eager_communication_budget.json
```

For event-driven simulations, `NcclMemoryModel.initialize_communicator(name)`
now materializes a profile's persistent buffers explicitly, without starting a
fake collective. Repeated initialization and later collectives reuse that same
backing. Omitting the call retains first-use initialization. HybridEP shared
backing can be started once with `OtherMemoryModel`; it must not be repeated for
every layer. The existing allocator timeline tests compare early and late NCCL
initialization under both fixed and expandable segment policies.

## Resource policy

The 256-GPU job **2978764 was canceled at the user's request before it ran**;
Slurm reports `CANCELLED` and elapsed time `00:00:00`. Full-scale GPU allocation
is not part of the memory-estimation workflow. This comparison runs on CPU;
future hardware calibration should use small, representative probes rather than
requesting all 256 GPUs. No new GPU job was submitted for this analysis.
